# ci-truth-serum

**A green check does not always mean the work passed.** These pre-commit lints find the places where CI reports success over a real failure. They are fast and they run offline.

Two things go wrong, and neither one shows up as a red check:

- **The pipeline hides a failure.** A pipe drops the exit code of the command that failed. Or a required check never reports, so the pull request waits forever.
- **You cannot prove what you ran.** A base image or a download names a tag or a bare URL. That target can change, so the bytes you run may differ from the bytes you reviewed.

## What it checks

### Honesty (Tier 1, default-on)

| Hook                              | Failure it prevents                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              | Example                                                                               |
| --------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| `check-workflow-pipefail`         | A pipe hides the exit code of every command except the last one. `pytest \| tee log` reports the result of `tee`. CI stays green after `pytest` fails. The check fires when a `run:` step uses a shell that does not set `pipefail`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             | `run: cat x \| jq .` — jq fails, the step exits 0                                     |
| `check-exit-suppression`          | `cmd \|\| true` discards the failure but keeps the output. A broken step then reports success. Example: a cleanup step did not release a resource, and the log still looks correct.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              | `npm test \|\| true` — the suite fails, the job is green                              |
| `check-stderr-suppression`        | `cmd 2>/dev/null` discards the error messages. When the command fails, you get a non-zero exit and no reason for it. Example: `docker compose up 2>/dev/null` hides why the container did not start.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             | `docker run … 2>/dev/null` — the launch dies with no reason in the log                |
| `check-substitution-exit-swallow` | A loop reads from `jq` or `yq` and ignores the exit code of that parser. A parse error then looks like an empty result. `done < <(jq …)` and `jq … \| while read` both do this. If `jq` fails on a renamed key, it exits non-zero, the loop runs zero times, and nobody sees the failure. The check covers `jq` and `yq` only. Opt out with `# allow-substitution-exit: <reason>`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               | `done < <(jq …)` — a jq query error empties the loop, exit 0                          |
| `check-argument-exit-swallow`     | A command substitution in an _argument_ throws away the exit status of the command inside it. `my_helper "$(risky_listing)"` runs `my_helper` on empty output after `risky_listing` fails. `set -e` does not stop the script, because the outer command succeeded. Shellcheck's SC2155 reports the same defect in `local x="$(cmd)"`, and it says nothing about this one. The check fires only when the outer command is a function that the same file defines, or a file it sources defines. Assign the output on its own line first, then pass the variable. Opt out with `# allow-argument-exit: <reason>`.                                                                                                                                                                                                                                                                                                                                                                                                                   | `my_helper "$(risky_listing)"` — the listing fails, the helper runs on empty input    |
| `check-soft-timeout`              | A time limit is only a request. `timeout 60 cmd` sends SIGTERM at the deadline, and a command can catch that signal, block it, or never reach its handler. The command then keeps running past the limit, and whatever waited on it keeps waiting. Measured: an `npm` install blocked on a dead registry socket outlived a 180-second limit by 8 minutes 36 seconds, and a wedged sandbox held an incident kill switch on its first target while every later target kept running. `--kill-after=N` schedules SIGKILL, which no process can catch, and that is what makes the limit real. The check reads the shell grammar, so it also finds the array form `run=(timeout 600)` that a text search cannot see. Opt out with `# allow-soft-timeout: <reason>`.                                                                                                                                                                                                                                                                    | `timeout 60 curl …` — the fetch ignores SIGTERM and the bound never ends it           |
| `check-pr-paths`                  | A `paths:`, `paths-ignore:`, or `branches:` filter on `pull_request` can skip the whole workflow. A required check then never reports, and the pull request waits at “Expected — Waiting” forever. Example: a branch filter skips a stacked pull request, because its base is not `main`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        | `pull_request: paths: ['src/**']` on a required check — a docs-only PR waits forever  |
| `check-pipefail-grep-pipe`        | A tested pipeline gives the wrong answer under `pipefail` when its last stage answers early. `grep -q`, `grep -m 1`, `head -5` and `sed 1q` all stop reading before the input ends. That stops the producer with SIGPIPE, and `pipefail` reports exit 141. Exit 141 reads as “no match”. Example: a check confirms that a secret is gone. It is wrong as soon as the listing is large enough to fill the pipe buffer. The check also reads a heredoc body that holds a shell script, because the file it writes out later runs.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  | `grep -q needle < <(gen)` under pipefail — a match returns 141, reads as no-match     |
| `check-frozen-head-sha`           | The event payload freezes at trigger time. `github.event.pull_request.head.sha` is the head commit from the moment GitHub queued the run, not the commit the job checked out. A force-push, or the routine autofix amend, moves the real head after that. A diff range against the frozen SHA then spans the whole branch history, because the frozen SHA is no longer an ancestor. A checkout of the frozen SHA can ask for a commit that no longer exists. Read the head from the checkout instead: run `git rev-parse HEAD` after `actions/checkout`. `base.sha` and `head.ref` are correct and stay untouched. The check reads each step's inline `run:` script and its `with:` values. It also follows an `env:` variable bound to the frozen SHA, and reports only where a step spends that variable in a `git` revision range or as a checkout `ref:`. Routing the expression through `env:` is the shape the template-injection checks want, so the binding alone is correct. Opt out with `# frozen-head-ok: <reason>`. | `ref: ${{ github.event.pull_request.head.sha }}` — the head moved after the trigger   |
| `check-ready-for-review`          | A workflow that skips its jobs while the pull request is a draft has deferred that work, not cancelled it. GitHub reports the pull request leaving draft as the `pull_request` activity type `ready_for_review`, and that type is not in the default set. A workflow that gates on the draft flag and omits the type never fires again. The draft run stays the last run, its gated jobs are `skipped`, and GitHub counts a skipped check run as a satisfied required check. The check judges two gate shapes: the workflow names `github.event.pull_request.draft`, or a job calls a reusable workflow with an input whose name carries `draft`. Opt out with `# ready-for-review-ok`.                                                                                                                                                                                                                                                                                                                                          | `on: pull_request` with a draft gate — marking the pull request ready starts no run   |
| `check-folded-scalar-comment`     | A `#` line inside a folded YAML scalar (`>` or `>-`) is not a comment. YAML folds the line into the **value**. If a shell then splits that value into arguments, the `#` opens a shell comment, and the shell drops every argument after it. Example: somebody adds an explanatory comment to a `claude_args: >-` block. The `--allowedTools` and `--add-dir` flags below it never reach the CLI, and the diff still reads as though the limits apply. The check judges only a folded block that also holds a line that starts with `-`, which marks an argument string rather than prose. A literal `\|` scalar keeps its newlines and stays out of scope. Opt out with `# allow-folded-scalar-comment: <reason>`.                                                                                                                                                                                                                                                                                                              | `args: >-` with a `# note` line — the note joins the value and eats the next argument |
| `check-gh-slurp-jq`               | `gh` refuses two argument sets: `--slurp` with `--jq` or `--template`, and `--slurp` without `--paginate`. It refuses them while it parses its arguments, before it sends any request. The call therefore exits non-zero on **every** run, so it has never worked. A site that discards that failure reports a permanent green. A site that does not discard it turns a scheduled job red every time. Example: a pagination helper uses `--slurp --jq '.[]'` and has returned nothing since the day somebody added it. The check reads a call that continues across lines, so a `--jq` on a later line still counts. Opt out with `# allow-gh-slurp-jq: <reason>`.                                                                                                                                                                                                                                                                                                                                                               | `gh api --slurp --jq .` — gh rejects the pair, so the call has never run              |

### Identity (Tier 1, default-on)

| Hook                        | Failure it prevents                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      | Example                                                                |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------- |
| `check-pinned-base-images`  | A Docker base image names a tag, and the registry can point that tag at different bytes at any time. `FROM node:22` today is not always the same image tomorrow. The check **requires a `@sha256:` digest**, so CI builds the image you reviewed.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        | `FROM node:22` — the digest behind the tag changes                     |
| `check-pinned-downloads`    | A script downloads a binary and runs it with no checksum and no signature. A tampered release or a compromised mirror can replace the file. The check also flags one-line installers such as `curl -fsSL … \| sudo sh`, which send unverified bytes straight into a shell. A `# pin-exempt`'d download still owes one proof: the saved file must not be empty when it runs. `curl -f` reports success on an empty response body. `bash`/`sh`/`source`/`.`/`chmod +x` on an empty file installs nothing, silently. The check flags the file's first run with no size check before it. Opt out with `# empty-download-ok: <reason>`.                                                                                                                                                                                                                                                                                                                                                                                                                                       | `curl -sL get.example.com \| bash` — no checksum, no signature         |
| `check-versionless-install` | An install command names no version. `pip install ruff`, `apt-get install -y docker-sbx`, `pipx install pre-commit`, and `npm install -g pnpm` all install whatever the index serves that day. This is worse than an unpinned image tag, because the version that changed appears nowhere in the diff. Example: a runtime installed with `apt-get install docker-sbx` served v0.37.1, while the version file in the repo pinned v0.35.0. The pin existed, and nothing at install time read it, which cost days of red end-to-end runs. The check covers shell scripts and inline workflow `run:` blocks. It leaves Dockerfiles to hadolint (DL3008, DL3013, DL3018). It also leaves these alone: a requirements or constraints file, a local path or archive, a URL or VCS spec, and a variable-built spec. It leaves a **local** `npm install pkg` alone too, because its range belongs in `package.json`. Opt out with `# pin-exempt: <reason>`. The recurring case is a distro package such as `apt-get install -y curl`, because apt serves one version per release. | `pip install pre-commit` — tomorrow’s CI runs a different pre-commit   |
| `check-provenance-repo-url` | A `package.json` or `pyproject.toml` still names the repository it was forked from. The first `npm publish --provenance` in the fork then fails with `E422 … Failed to validate repository information`, because the URL names the upstream repo. The check compares the declared repository URL against the publishing repo, and never reads `Homepage`. It takes the publishing repo from `$GITHUB_REPOSITORY`, which is the name npm signs into the bundle, and falls back to your `origin` remote. A rename keeps the old URL in every clone's `origin`, so on a mismatch the check follows the redirect with one `git ls-remote` and accepts the new name. A mismatch has no opt-out: a fork must correct its URL. The check skips a repo with no `origin` remote and no `$GITHUB_REPOSITORY`.                                                                                                                                                                                                                                                                      | a fork's `repository.url` still names upstream — npm publish dies E422 |

### Security (Tier 1, default-on)

| Hook                        | Failure it prevents                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          | Example                                                                   |
| --------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| `check-trusted-base`        | This is the “pwn-request” hole. A `pull_request` or `pull_request_target` job checks out the code of the pull request **and** holds write permissions or secrets. The code of an outside contributor then runs with the credentials of your repo, and it can read your secrets. The check also catches the same job when it checks out a **base** ref that the author chose. The author picks the base branch. A job that stages “the base branch” can therefore read a branch that carries a rewritten build script. The diff of the pull request stays clean. A narrower base of `main` or `master` is not a fix. On a repo whose default is `main`, `master` is an ordinary branch that anyone can push. A base context used as _data_, such as a diff range or a version baseline, is not reported. Only a base context passed to `actions/checkout` is reported. A read-only checkout with no secrets is the safe way to lint untrusted code, and it passes. Opt out with `# trusted-base-ok: <reason>`.                                                                                                                                                                                                                                                                                                                                | checkout `base.ref` + a write token — the PR author picks the base branch |
| `check-untrusted-exec`      | The same job **runs** the checked-out pull-request code while secrets are live. Three shapes do this. A local composite action (`uses: ./…`) has a manifest that GitHub reads from the workspace. A package-manager script (`pnpm build`, `npm run test`, `make release`, `npx …`) has a body that comes from the checked-out `package.json` or `Makefile`. A workspace-relative path (`bash ./scripts/x.sh`) is a file from the checkout. Example: the pull request rewrites the `build` script in `package.json`, and your release PAT is in the environment when that script runs. The check reaches jobs that `check-trusted-base` cannot see, such as a job with a matrix-derived head ref, or an unpinned `workflow_run` head. It also reports a job whose `# trusted-base-ok` reason claims that the job “only runs the trusted base copy”. The entrypoint itself still comes from the workspace. Staging scripts into `$RUNNER_TEMP` is not a defence: an earlier attacker step in the same job owns `$GITHUB_ENV`, `$GITHUB_PATH`, and that directory. Opt out with `# untrusted-exec-ok: <reason>` in the job block.                                                                                                                                                                                                               | checkout PR head, then `uses: ./.github/actions/setup` with secrets live  |
| `check-unscoped-tool-grant` | A Claude Code tool grant is unscoped or inert. The grant can be `--allowedTools`, an `*ALLOWED_TOOLS` env var, or an `allowed_tools:` input. A file tool named with **no path** — `Read`, `Grep`, `Glob`, `Write`, `Edit` — grants the whole tool. Claude Code applies that grant _after_ the per-path working-directory check and overrides its verdict. An `--add-dir` beside it therefore suppresses a prompt instead of building a jail. A path rule spelled under any name except `Read` or `Edit` is a rule that **nothing reads**: `Write(//out.json)` denies the write it appears to grant. `Edit(...)` is the spelling that confines Edit, Write, MultiEdit, and NotebookEdit, and an absolute path needs two leading slashes. These rules come from probes of the real CLI, run headless against a stub API, and each case had a matched denying control. The behaviour is undocumented. The docstring therefore names the CLI version it was measured on, and it asks you to probe again on a much newer CLI. Opt out of the unscoped half with `# allow-unscoped-read-grant: <reason>` or `# allow-unscoped-write-grant: <reason>`. That is reasonable when the same job also grants bare `Bash`, because a redirect can write anything. The inert half has **no** opt-out: a rule that nothing reads is never correct to write. | `--allowedTools Read` — reads `/proc/self/environ`, not just the repo     |

### Opinionated (Tier 2, opt-in)

These checks assume an architecture. Enable them only if you follow it.

| Hook                               | Failure it prevents                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      | Example                                                                                        |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------- |
| `check-always-reporter`            | A gate job skips every real work job, so a required check stays at “Expected — Waiting”. The check assumes that you use a **decide job plus an `always()` reporter** job.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                | a gated job with no `always()` reporter — `skipped` never reports a status                     |
| `check-required-reporter`          | A new `always()` reporter is green, but nobody added it to the required list in branch protection. It therefore gates nothing. The check assumes that the required list mirrors these annotations. A `uses:` job marked `# required-check: true` reports under a name the marker cannot predict, so the sync can never match it to a real check run either.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              | a reporter with no `# required-check:` marker — or the marker on a `uses:` job                 |
| `check-required-event-closure`     | A job that a required check `needs` skips on an event the check gates, for example a `decide` job that skips in the merge queue. GitHub counts the skipped check run as satisfied, so the check reports green there with none of its work done. The check reads the same `# required-check: true` markers.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               | a needed job whose `if:` provably excludes a gating event — a silent green                     |
| `check-job-timeout`                | A job declares no `timeout-minutes`, so it inherits the GitHub default of 360 minutes. A hung test, or a network fetch with no deadline, can then hold a shared runner for **six hours**. The check requires every job to set its own limit. A job that calls a reusable workflow with `uses:` is exempt, because `timeout-minutes` is not valid there. Opt out with `# allow-no-timeout: <reason>`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     | no `timeout-minutes:` — a hung step holds a runner for the 6-hour default                      |
| `check-uncached-download`          | A job downloads a version-pinned tool and holds no cache. The bytes cannot change, because the version is pinned, so every push to every pull request pays for the same fetch. The cost is invisible: the step is green, and the waste shows up as minutes on the job clock. When a registry is slow, the job runs past its `timeout-minutes`, and GitHub reports that as **cancelled** with one log line, “The operation was canceled.” In one real case a test shard with a 15-minute budget spent 7.9 minutes in a single `npm install -g` of a pinned package, and three shards went cancelled together. The check inlines local composite actions first, so a job that caches through a shared setup action counts as cached. It leaves an unpinned install alone, because that has no stable cache key. Opt out with `# cache-exempt: <reason>`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   | `curl -O .../v2.12.0/tool` with no `actions/cache` — every PR refetches it                     |
| `check-inline-run-length`          | A long inline `run:` script ships unchecked. shellcheck, shfmt, and shellharden read standalone `.sh` files, not inline blocks. A long inline script can therefore hide an unquoted variable or a missing `pipefail`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    | a 60-line `run:` block — shellcheck never sees it                                              |
| `check-concurrency`                | A `concurrency:` block omits `cancel-in-progress`, which defaults to `false`. A new push then queues behind a stale run instead of cancelling it.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        | `concurrency:` with no `cancel-in-progress:` — the default is not what you expect              |
| `check-static-concurrency`         | A workflow-level `concurrency.group` carries no per-ref key, such as `github.ref` or `head_ref`. A run from another branch can then cancel the pending run of this branch before any job starts. The `always()` reporter never runs, and a required check waits forever. The check also asks whether the key holds a value on each event the workflow declares. `github.head_ref` is empty off a pull request. `github.ref` is the default branch on an event that carries no ref of its own, such as `workflow_run` or `schedule`. On those events a group keyed only on them is one static string again.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               | `group: build` on a required check — a superseded run starts zero jobs                         |
| `check-conclusion-coverage`        | A workflow-run listener, a shell router, or a Python scanner treats only `failure` as red. GitHub also returns `timed_out`, `startup_failure` and `action_required`, so a run that ends in one of those reaches nobody, and nothing goes red — the code that decides what red means is the code that skipped it. The observed case held three copies of the answer in one repository, written months apart. The check reads a workflow expression, a `[[ ]]`/`case` test, and a Python comparison or membership test, each through its own parser, and names the conclusions the site left out. An `if`/`elif` chain and a `case` are one decision, so a classifier split over branches is judged whole. A site is judged only when it recognizes `failure` itself, so a test for one specific cause, for `success`, or for `cancelled` alone is left alone, and so is a negation such as `!= 'success'`, which already covers everything. `cancelled` is never required: a run a newer push supersedes ends there in normal operation. Widen the set for the whole repository with `extra:` in `.github/conclusion-coverage.yml`. Opt out with `# allow-conclusion-subset: <reason>`.                                                                                                                                                                                                                                                                                   | a notifier matches `conclusion == 'failure'` — a timed-out run tells nobody                    |
| `check-cancellable-required-check` | A workflow-level `concurrency.group` is both static and cancellable, on a workflow that declares a required check with `# required-check: true`. A run from a sibling ref shares the one static slot and cancels this run whole. The block sits at the **workflow** level, so the cancellation removes every job, including the `always()` reporter. `always()` does not survive a run-level cancel. No status reaches the head of this ref, and the required check waits forever. `check-static-concurrency` cannot see these workflows. It looks for a decide gate plus a reporter, and a workflow can declare a required check with the marker alone. A group counts as static when its per-ref key is empty or fixed on one of the workflow's events. A group that keys on `github.head_ref` and falls back to `github.ref` is one example. It names the default branch on every `workflow_run` run. Three fixes work: key the group per ref or per run, move the `concurrency:` block onto the expensive job, or set `cancel-in-progress: false`. Opt out with `# cancellable-required-check-ok`.                                                                                                                                                                                                                                                                                                                                                                   | a static cancellable group on a `# required-check: true` workflow                              |
| `check-pending-cancel-concurrency` | A configuration turns a required check **red for no real reason**. Several runs queue on one commit when `on.pull_request.types` names types beyond opened, synchronize, and reopened. `labeled` is the common one, and a Dependabot pull request arrives with labels already set. A per-PR `concurrency.group` then lets GitHub cancel one of those same-commit runs. Its `always()` reporter reports “cancelled”, which is a red mark with no real failure. `cancel-in-progress` does not help. Drop the group, or key it on `github.run_id`. The check reads a workflow that declares a required check by either route: a decide gate with an `always()` reporter, or a `# required-check: true` marker on one job. On the marker route it reads the marked jobs only. Opt out with `# pending-cancel-ok`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            | a cancelled pending run reports nothing, so the required check never resolves                  |
| `check-requires-concurrency`       | A `pull_request` or `pull_request_target` workflow declares **no** `concurrency:` block at all. Every push to a pull request then starts a second full run instead of cancelling the first, which drains a limited runner pool. `check-concurrency` reads a block that exists; this check requires the block. A block at the workflow level or the job level satisfies it. Opt out with `# concurrency-not-required`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    | a PR workflow with no lock — two runs race on the same branch                                  |
| `check-externalized-markers`       | A workflow guard scans inline `run:` blocks for a required marker. It goes blind as soon as that command moves into a `.github/scripts/*.sh` file or a composite action. Example: a guard requires `fetch-depth: 0` whenever a history-rewrite command runs. The guard stops seeing the command once it lives in a script, and it passes while the requirement is unmet.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 | a `run:` that calls a script the guard cannot read                                             |
| `check-path-gate-deps`             | A gated job skips, and its `always()` reporter goes green, on the exact pull request that changed a file the job needs. This happens when the path filters of the decide job omit a composite action or a `.github/scripts/` helper. The check confirms that the filters cover every dependency of every gated job: composite actions, scripts sourced one hop deep, and paths declared with `# gate-deps:`. Suppress one dependency with `# path-gate-ok: <dep> <reason>`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              | a `decide` regex omits a composite action — the job skips exactly when it changed              |
| `check-reusable-permissions`       | A job that calls a reusable workflow with `uses: ./.github/workflows/…` hands its own token to that workflow. The called workflow can lower the grant. It can never raise it. Somebody adds a permission to the shared workflow, and every caller that grants less fails at the start of the run. The error names the callee, not the caller, so it points away from the file that must change. The check reads the `permissions:` blocks of both sides and compares them. It follows the call one more hop when the middle job declares no block of its own. A caller that declares no block at all is reported too: the token then carries the repository default, which the workflow file does not state. Suppress one calling job with `# reusable-permissions-ok: <reason>`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        | `pull-requests: read` lands in the shared path filter, and every gated workflow stops starting |
| `check-failure-notifier-coverage`  | A new push or schedule workflow fails silently, because nobody added it to the `on.workflow_run.workflows` list of the failure notifier. `workflow_run` accepts no wildcard, so somebody maintains that list by hand. The check finds the notifier by **shape**: a workflow triggered `on.workflow_run` that names a notification sink. It never finds the notifier by filename, and it treats “no notifier at all” as a **failure** rather than a silent pass. Every listed name must match a real workflow. The list must cover every push or schedule workflow whose failure reaches nobody else, which is less than the whole tree. A workflow that notifies on its own failure, that also runs on `pull_request`, or that carries a reasoned `# cron-alert: false` belongs to somebody else. A red check on a pull request already reaches a reviewer, and demanding coverage here would page twice or overrule the opt-out. A longer list than that minimum is allowed. ## Usage

These are [pre-commit](https://pre-commit.com) hooks. Install pre-commit and
enable its git hook:

```bash
pipx install pre-commit # or: pip install pre-commit / brew install pre-commit
pre-commit install
```

Then add ci-truth-serum to your `.pre-commit-config.yaml`. The block below
enables Tier 1, which is honesty plus identity. Tier 2 and Extras are commented
out, so uncomment what you want. pre-commit builds an isolated Python
environment for each hook, so pre-commit is the only prerequisite.

```yaml
repos:
  - repo: https://github.com/AlexanderMattTurner/ci-truth-serum
    rev: v1.0.0 # the release tag; matches the package version (vX.Y.Z)
    hooks:
      # ── Tier 1 · Honesty (default-on) ──
      - id: check-workflow-pipefail
      - id: check-exit-suppression
```

### Enable a whole tier with one id

You can enable a tier aggregate instead of adding a new `- id:` every time a
check ships. One id runs every Python check in that tier, and a check added
later arrives with **no change to your config**:

```yaml
repos:
  - repo: https://github.com/AlexanderMattTurner/ci-truth-serum
    rev: v1.0.0 # the release tag; matches the package version (vX.Y.Z)
    hooks:
      - id: check-tier1 # every honesty + identity check (the safe default-on set)
      # - id: check-tier2   # every opinionated check: it assumes the decide-gate + reporter architecture
      # - id: check-extras  # the Python extras (vendor-specific or style-specific)
```

Three checks are in no aggregate. Add each `- id:` on its own if you want it:

- `check-absolute-symlinks` is a shell `language: script` hook, not a Python module.
- `check-lockstep-pins` is config-driven. It hard-errors without the per-repo
  `--pair` arguments that an aggregate cannot supply.
- `check-env-symmetry` scans the whole tree and needs a per-project `--prefix`
  argument that an aggregate cannot supply.

You may mix an aggregate with individual ids. The named check then simply runs
twice.

### Select by tag

A tier says how much of your CI architecture a check assumes. A tag says what the check is about. The two are different questions, so a check carries one tier and as many tags as apply: `check-token-fallback` is `secrets` and `security` at once.

Select on either axis with `check-select`. It takes `--select` (repeatable, union) and `--ignore` (repeatable, subtraction):

```yaml
repos:
  - repo: https://github.com/AlexanderMattTurner/ci-truth-serum
    rev: v1.0.0
    hooks:
      - id: check-select
        args: [--select, "tag:security", --select, "tag:secrets"]
```

A selector is one of these four forms:

| selector                    | selects                                            |
| --------------------------- | -------------------------------------------------- |
| `all`                       | every aggregated check in the pack                 |
| `tier:<1\|2\|extras>`       | every check in that tier (what `check-tier1` runs) |
| `tag:<name>`                | every check carrying that tag                      |
| `check:<module-or-hook-id>` | one check, written either way                      |

Tier 1 without its Docker lint is one line:

```yaml
- id: check-select
  args: [--select, "tier:1", --ignore, "check:check-pinned-base-images"]
```

Three cases exit 2 instead of running a smaller set: no `--select` at all, a selector this pack does not ship, and a selection that ends up empty after the `--ignore` values. A hook that runs zero checks and reports success is the false green this pack exists to refuse.

The tag vocabulary is closed. These are the values:

| tag               | the defect it is about                                                        |
| ----------------- | ----------------------------------------------------------------------------- |
| `honesty`         | a failure that reports success: a masked exit code, a parsed error string     |
| `supply-chain`    | code that runs without naming what it is: a mutable tag, an unpinned download |
| `security`        | privilege or untrusted input reaching a place it must not                     |
| `secrets`         | a token or a secret file handled so its absence passes as its presence        |
| `required-checks` | a required check that never reports, or reports on the wrong events           |
| `concurrency`     | a concurrency group that cancels or strands the run a merge waits on          |
| `scheduling`      | a cron whose schedule, target, or gating does not do what it says             |
| `alerting`        | a failure that reaches no human                                               |
| `docs`            | narration that contradicts the tree it describes                              |
| `tests`           | a test that passes without testing anything                                   |
| `agents`          | an AI-agent surface: a model pin, a tool grant, tool markup left in a file    |
| `correctness`     | ordinary logic defects the other tags do not cover                            |
| `maintainability` | code shaped so the next reader cannot see what runs                           |
| `cost`            | CI minutes spent on a run that cannot finish or did not need to start         |

A tag is not a file type. The files a check reads come from its own `types:`, so there is no `shell` or `python` tag to restate them.

The three checks that sit in no aggregate carry no tag either, so no selector reaches them. `check-absolute-symlinks`, `check-lockstep-pins`, and `check-env-symmetry` stay standalone ids.

### Scope one check to specific paths

One check in a tier can need tighter file scoping than the rest. For example,
`check-exit-suppression` may be too strict for your `tests/` directory. Use
`--skip <module_name>` to drop that check from the aggregate. Then add it again
as a standalone hook with the usual pre-commit `files:` and `exclude:` filters:

```yaml
- repo: https://github.com/AlexanderMattTurner/ci-truth-serum
  rev: v1.0.0
  hooks:
    - id: check-tier1
      args: [--skip, check_exit_suppression] # drop it from the aggregate...
    - id: check-exit-suppression # ...then add it again with scoped filters
      files: '^(bin/|setup\.bash$|\.devcontainer/|\.claude/hooks/)'
      exclude: "^bin/(bench-|check-)"
```

`--skip` is repeatable: pass one `--skip <name>` pair per check you drop. **An
unknown name is a hard error**, which catches a typo that would otherwise
include the check again in silence. Module names use underscores and match the
registry in `ci_truth_serum/_registry.py`. Write `check_exit_suppression`,
not `check-exit-suppression`.

This keeps the property that matters. A new check added to the tier upstream
still arrives automatically through the aggregate. You opt out only of the
checks you scope on purpose.

`check-exit-suppression` also takes `--producer-only`, which restricts it to
the captured-producer rule (a suppressed `$(gh api …)`/`$(jq …)` capture) and
skips the uncaptured rule (a bare `cmd || true` with output kept). A consumer
that wants the producer rule over a wider tree than it has ever enforced the
uncaptured rule on adds a second `check-exit-suppression` entry with that flag
and a broader `files:`, instead of widening the first entry's scope and
inheriting uncaptured findings it never opted into.

### Autofix (opt-in): digest-pin base images

`check-pinned-base-images` can rewrite what it finds. Pass `--fix`, and it
resolves the current registry digest of each unpinned `FROM` and appends it, so
`FROM node:22` becomes `FROM node:22@sha256:…`. It preserves a `--platform` flag
and an `AS <stage>` suffix. The flag is opt-in because `--fix` makes the only
network call in the pack, a Docker Registry v2 manifest lookup. Detection stays
offline. The check leaves an image untouched when it cannot resolve the digest,
and it never guesses one.

```yaml
- id: check-pinned-base-images
  args: [--fix]
```

### Apply: mirror branch protection from the annotations

`check-required-reporter` lints locally, and `sync-required-checks` applies. It
reads every job marked `# required-check: true`, which is any job and not only
an `always()` reporter. It expands each `name:` across its `strategy.matrix`
into concrete check contexts. It then rewrites the branch-protection ruleset of
the repo, so `required_status_checks` matches that set exactly. The annotations
become the single source of truth, and the required set stops drifting in the
GitHub UI.

A `uses:` job (a reusable-workflow call) can never carry the marker, because
`sync-required-checks` derives the context from that job's own `name:`, while
GitHub reports its check run as `<caller job name> / <called job name>`. The
lint rejects that combination; put the marker on a caller-local reporter job
that `needs:` the call instead.

```bash
pip install "git+https://github.com/AlexanderMattTurner/ci-truth-serum@v1.0.0"

# Report drift and exit non-zero WITHOUT mutating (PR-safe gate):
sync-required-checks --repo owner/name --check

# Rewrite the ruleset to match the annotations:
GH_TOKEN=<token-with-administration:write> sync-required-checks --repo owner/name
```

The mutation path needs a token in `GH_TOKEN` or `GITHUB_TOKEN` with
`administration: write`. It reads the marker from the same scoped lines that the
lint classifies, so the gate and the apply step can never disagree. Pass
`--ruleset-id` if the repo has more than one branch ruleset.

### Apply: keep a merge queue able to merge

`sync-merge-queue` reads the merge queue rule of the same branch ruleset. A merge queue stops merging when two of its parameters change, and nothing turns red: GitHub builds each group, watches every check pass, and merges none of them. The script repairs those two parameters and leaves every other parameter as a human set it.

- `grouping_strategy` is pinned to `ALLGREEN`. Under `HEADGREEN` an entry merges on another entry's build, so an untested change reaches the branch. Pass `--allow-headgreen` for a repo whose checks re-test the whole group.
- `max_entries_to_merge` and `max_entries_to_build` must be above zero. A zero lets a group hold no entry at merge time. The repair writes `1`, and any positive size survives.

Three more states stop every merge, and only a human can fix them. The script reports each one and exits non-zero: a ruleset that is not enforced, a queue whose `merge_method` the repo settings forbid, and a ruleset with no always-on bypass for the merge queue app. The queue merges a group by a push outside any pull request, so a bypass scoped to pull requests does not cover it. Pass `--skip-bypass-check` for a repo whose ruleset never refuses that push.

```bash
# Report what is broken and write nothing:
GH_TOKEN=<token-with-administration:write> sync-merge-queue --repo owner/name --check

# Repair the two parameters, then read the ruleset back:
GH_TOKEN=<token-with-administration:write> sync-merge-queue --repo owner/name
```

Run it on each push to the default branch, beside `sync-required-checks`. A repo whose branch ruleset carries no merge queue rule exits 0 and says so.

### Config: enforce twin pins with check-lockstep-pins

`check-lockstep-pins` replaces a “keep these in lockstep” comment with a gate.
The motivating pair is a `rev:` in `.pre-commit-config.yaml` and a
`pip install git+…@` pin of the same release in a workflow:

```yaml
- id: check-lockstep-pins
  args:
    - --pair
    - .pre-commit-config.yaml
    - 'ci-truth-serum\s+rev:\s*(\S+)'
    - .github/workflows/lint.yaml
    - 'ci-truth-serum\.git@(\S+)'
```

Each regex needs exactly one capture group, and it must match exactly once in
its file. Zero matches means the pattern rotted, and several matches are
ambiguous; both are a hard error. The two captures must be equal. Repeat
`--pair` for more pins.

### Apply: verify a release with release-canary

`release-canary` confirms that the places where a release leaves its version
agree. It reads two markers: the semver-max `v*` git tag, and the top dated
`## [x.y.z]` heading in the changelog. It skips a `## Unreleased` heading. If
the repo also ships to the AUR, the `pkgver=` line in a `PKGBUILD` is a third,
optional marker. The tool reads that marker only when a PKGBUILD is present, so
it catches a forgotten bump and leaves a repo without one unaffected. It skips a
build-time `pkgver()` that it cannot read offline, and it never treats that as a
failure. The tool reports a marker that is absent entirely as a missing marker. A changelog that somebody rolled but never tagged is the common case, and that is what a half-finished release looks like. On a mismatch the tool prints every present value
with its label and exits non-zero. **The tool reads every marker locally, so it
makes no network request and needs no registry credentials.** It runs in the
same restricted job that cut the release.

```bash
pip install "git+https://github.com/AlexanderMattTurner/ci-truth-serum@v1.0.0"

release-canary                           # tag + changelog in the current repo
release-canary --changelog CHANGELOG.md --repo-dir .
release-canary --pkgbuild aur/PKGBUILD   # a non-default PKGBUILD location
```

Run it as a post-release workflow step. It then catches two failures the same day rather than at the next release. The first is a publish that died after tagging. The second is a tag push that returned 403 after publishing.

### Apply: find the failures nothing reported with startup-failure-scan

`startup-failure-scan` names the workflows whose runs failed before any job started. GitHub creates a run for a workflow file it cannot load. The run completes, it carries a failure, and it holds zero jobs. Every route that reports a failure needs a job, so this one route reaches nobody:

- a notifier that watches through `on.workflow_run` reports per job, and this run has none to name;
- an `if: always()` reporter is itself a job, so it never runs, and a required check waits at `Expected — Waiting` instead of turning red;
- the pre-commit lints in this pack cannot see the file either, because the YAML that a parser accepts is a larger set than the YAML that the Actions loader accepts.

The tool reads run history, so it needs the API and a token. It is not a pre-commit lint, and no tier aggregate runs it. Run it from a weekly health job:

```bash
pip install "git+https://github.com/AlexanderMattTurner/ci-truth-serum@v1.0.0"

GH_TOKEN=<token-with-actions:read> startup-failure-scan --repo owner/name
startup-failure-scan --repo owner/name --window-days 14 --format markdown
```

The scan reads the whole window for each workflow, and not the newest page of it. That matters on a busy repo: a workflow that runs 100 times a day puts 700 runs in a 7-day window, and a scan that read only the first 100 would answer about the last day while the report said a week. It exits non-zero when it finds anything; pass `--report-only` for a job that only publishes the report. `--format markdown` prints a table to paste into a tracking issue. This repo runs the scan every Monday; copy `.github/workflows/startup-failure-scan.yaml` for the whole job, which needs only the `actions: read` permission.

The cost is one request for each 100 completed runs, plus one for each failing run that did not conclude `startup_failure`. A successful run costs nothing. The Actions API stops paginating at 1000 items, so one workflow costs at most 10 listings. A workflow busier than that is the one case the scan cannot read in full, and the report names it and marks its count as a floor.

**The obvious version of this scan reports every repo healthy.** A run that failed to load concludes `startup_failure`, and not `failure`. The `status=` filter on the runs listing matches the conclusion, so `status=failure` never returns one. This tool asks for `status=completed` and classifies each conclusion itself. It leaves out `cancelled` and `skipped`, because a run cancelled in the queue also holds zero jobs and is not a broken file.

## It complements other tools, it does not replace them

ci-truth-serum enforces policy gaps. Keep running the tools it does not
duplicate:

- [`zizmor`](https://github.com/woodruffw/zizmor) pins `uses:` references to a
  SHA.
- [`hadolint`](https://github.com/hadolint/hadolint) checks Dockerfiles.
  `check-pinned-base-images` is stronger: it demands a `@sha256:` digest, not
  only an explicit tag.
- [`actionlint`](https://github.com/rhysd/actionlint) checks workflow syntax and
  types.
- `shellcheck` checks shell.
